# 05. Pi 스트리밍 / 대역폭 계산

Pi는 **"전송만"**. 여기서 대역폭 계산을 꼭 한다.

## 숫자
| 구성 | 대역폭 | 판정 |
|------|--------|------|
| 스테레오 1280×960 모노 ×2 @30fps raw | ≈ **590 Mbps** | USB Wi-Fi 동글로 사실상 불가능 |
| 640×480으로 낮춤 (×4↓) | ≈ **150 Mbps** | 아직 무거움 |
| + MJPEG 압축(≈10:1) | ≈ **15 Mbps** | **현실권** ✅ |

- **ORB-SLAM3는 640×480에서도 잘 돈다.** 굳이 풀해상도 안 보내도 됨.

## 함정 2개
1. **Pi 5는 하드웨어 H.264 인코더가 빠졌다** (Pi 4엔 있었음).
   → H.264 소프트 인코딩은 CPU를 먹음. **MJPEG가 CPU 부담 적음 → 시작은 MJPEG 권장.**
   (사용자는 USV에서 Flask MJPEG 경험 있음 → 익숙할 것.)
2. **저지연을 위해선 Flask TCP보다 GStreamer RTP/UDP가 훨씬 낫다.**
   ```
   v4l2src → jpegenc → rtpjpegpay → udpsink   (Pi)
   udpsrc  → rtpjpegdepay → jpegdec → ORB-SLAM3  (데스크톱)
   ```

## 강력 제안: 동공 검출은 Pi에서
- **대역폭상 압도적으로 유리.** pye3d는 무거운 NN이 아니라 고전 알고리즘에 가까움.
  → 크롭된 눈 영상 기준 **Pi 5 CPU에서 30~60fps**.
- 그러면 눈 카메라 영상 스트림 전체(≈150 Mbps)를 안 보내고 **시선벡터 몇 바이트만** 전송.
  → 스테레오 영상만 무선으로 넘기면 됨.
- **프레이밍**: "Pi가 주 처리를 한다"가 아니라 **"센서 옆에서 전처리해 대역폭을 아낀다"**.
  - 교수님이 Jetson 대신 Pi로 방향 잡으신 취지("무거운 추론은 Pi에서 하지 말라")와 충돌 안 함.
    동공 검출은 무거운 추론이 아니라 **센서 전처리**에 가까움.
  - **결정은 교수님과 상의**하되, 대역폭 이득이 워낙 커서 강하게 추천.
