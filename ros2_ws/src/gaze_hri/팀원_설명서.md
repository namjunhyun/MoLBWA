# 로봇 쪽, 쉽게 설명합니다

팀원들에게 "우리가 로봇 쪽에서 뭘 만들고 있는지"를 설명하는 문서입니다.
ROS2를 한 번도 안 써봤어도 읽을 수 있게 썼습니다.

**7번과 8번이 제일 중요합니다.** 좌표가 어떻게 만들어지는지,
컵이 여러 개일 때 어떻게 구분하는지가 이 프로젝트에서 가장 헷갈리는 부분입니다.

---

## 1. 우리가 만드는 게 뭔가

> **컵을 쳐다보면, 로봇팔이 그 컵을 집어서, 내가 쳐다본 자리로 옮겨준다.**

손이나 팔을 못 쓰는 사람도 눈만으로 물건을 옮길 수 있게 하는 시스템입니다.

전체는 크게 두 덩어리입니다.

| | 하는 일 | 결과물 |
|---|---|---|
| **안경 쪽** | 눈이 어디를 보는지 알아냄 | 3D 좌표 하나 |
| **로봇 쪽** | 그 좌표로 컵을 집어 옮김 | 로봇 동작 |

이 문서는 **로봇 쪽** 이야기입니다.

---

## 2. 왜 따로 만드나

안경 쪽은 아직 개발 중입니다. IR 카메라도 늦게 도착했고 SLAM도 튜닝 중이죠.
로봇 쪽이 안경을 기다리면 시간이 두 배로 듭니다.

그래서 **"좌표는 어디선가 온다고 치고"** 로봇 쪽만 먼저 완성합니다.
좌표를 만드는 사람은 지금 **마우스**입니다.

```
[지금]   마우스 클릭 ──> 좌표 ──> 로봇이 집어서 옮김
[나중]   시선       ──> 좌표 ──> 로봇이 집어서 옮김
                      ↑
              여기만 갈아끼우면 끝
```

로봇 쪽 코드는 좌표가 어디서 왔는지 **관심이 없습니다.**
그래서 나중에 합칠 때 로봇 쪽은 거의 안 건드려도 됩니다.

---

## 4. ROS2가 뭔가

### 한 줄 요약

> **작은 프로그램 여러 개를 만들고, 서로 데이터를 주고받게 하는 방식.**

하나의 큰 프로그램 대신, 일을 잘게 쪼개서 각각 독립된 프로그램으로 만듭니다.

### 용어 세 개만 알면 됩니다

**노드 (Node)** = 작은 프로그램 하나.
우리는 노드를 5개 만들었습니다. 각자 한 가지 일만 합니다.

**토픽 (Topic)** = 노드끼리 데이터를 흘려보내는 통로.
방송국 같은 겁니다. 한 노드가 라디오처럼 계속 송출하고, 듣고 싶은 노드가 주파수를 맞춥니다.

**발행(publish) / 구독(subscribe)** = 송출한다 / 듣는다.

```
[노드 A] ──발행──> /gaze/point_raw ──구독──> [노드 B]
                    (토픽 이름)
```

### 왜 이렇게 하나

- **한 군데가 죽어도 나머지는 산다.** 카메라 노드가 꺼져도 로봇 노드는 멀쩡합니다
- **어디가 문제인지 바로 안다.** 토픽을 들여다보면 신호가 어디서 끊겼는지 보입니다
- **갈아끼우기 쉽다.** 마우스 노드를 시선 노드로 바꿔도 나머지는 그대로
- **팀 작업이 쉽다.** 각자 다른 노드를 맡으면 충돌이 안 납니다

### 실제로 쓰는 명령어는 세 개뿐

```bash
ros2 launch gaze_hri robot_only.launch.py   # 전부 한 번에 켜기
ros2 topic echo /gaze/target                # 이 통로에 뭐가 흐르는지 보기
ros2 topic list                             # 통로 목록 보기
```

`ros2 topic echo`는 **전기 테스터** 같은 겁니다. 선에 신호가 흐르는지 찍어보는 거죠.
문제가 생기면 앞에서부터 하나씩 찍어보면 어디서 끊겼는지 나옵니다.

## 5. 노드 5개가 각각 뭘 하나

컵을 집어 옮기는 과정을 다섯 명이 나눠서 한다고 생각하세요.

### ① topdown_click — "좌표를 만드는 사람"

일을 **두 가지** 합니다. 나중에 운명이 갈리니 구분해서 기억하세요.

**일 1: 마우스 좌표 만들기 (임시)**
탑다운 카메라 영상을 창에 띄우고, 마우스 커서 위치를 좌표로 바꿔 흘려보냅니다.
클릭하면 그 자리에 2초간 고정합니다.
→ **나중에 안경(`gaze_bridge`)으로 교체됩니다.**

**일 2: 컵 위치 찾기 (계속 씀)**
화면에서 컵들을 찾아 좌표 목록을 만듭니다.
→ **안경을 붙인 뒤에도 그대로 씁니다.** 오히려 이때 더 중요해집니다.

> 발행: `/gaze/point_raw` (좌표 하나), `/objects/poses` (컵들의 좌표 목록)

### ② dwell_detector — "진짜 고른 건지 판단하는 사람"

좌표가 계속 흘러들어오는데, 그게 전부 "선택"은 아닙니다.
시선은 1초에도 몇 번씩 튀니까요.

그래서 **한 곳에 1.2초 동안 머물렀을 때만** 통과시킵니다.

> 구독: `/gaze/point_raw` → 발행: `/gaze/fixation`

### ③ target_resolver — "어느 컵인지 판단하는 사람"

**이 노드가 이 시스템의 판사입니다.** 8번에서 자세히 다룹니다.

- 시선이 준 좌표 하나와, 탑다운이 준 컵 좌표 목록을 받습니다
- 거리를 재서 가장 가까운 컵을 고릅니다
- 집을 때는 **컵 중심**으로, 놓을 때는 **테이블 높이**로 보정합니다

> 구독: `/gaze/fixation` + `/objects/poses` → 발행: `/gaze/target`

### ④ task_manager — "순서를 관리하는 사람"

지금이 "집을 걸 고르는 중"인지 "놓을 자리를 고르는 중"인지 기억합니다.

```
IDLE ──첫 번째 선택──> PICK_SELECTED ──두 번째 선택──> EXECUTING
  ▲                                                      │
  └──────────────── 동작 끝나면 ──────────────────────────┘
```

안전장치도 여기 있습니다.
- 놓을 자리가 집을 자리와 10cm 이내면 거부 (실수 방지)
- 15초 동안 두 번째 선택이 없으면 자동 취소

> 구독: `/gaze/target` → 로봇에게 작업 지시

### ⑤ arm_server — "실제로 움직이는 사람"

좌표를 받아서 관절 각도를 계산하고 모터를 돌립니다.

```
접근 → 하강 → 그리퍼 닫기 → [잡았는지 확인] → 들기
     → 이동 → 하강 → 놓기 → 복귀
```

**"잡았는지 확인"이 중요합니다.** 물체를 물면 그리퍼가 끝까지 안 닫히거든요.
그 차이로 성공/실패를 판별하고, 실패하면 최대 3번까지 다시 시도합니다.

> 구독: 작업 지시 → 서보 모터 제어

## 7. 좌표는 어떻게 만들어지나 ★

여기가 제일 헷갈리는 부분입니다. 천천히 읽어주세요.

### 먼저 용어 정리

> **"탑다운 카메라 기준 좌표" 같은 건 안 만듭니다.**
> 기준은 언제나 **로봇 베이스**입니다.

모든 좌표는 "로봇 밑판 중심에서 앞으로 몇 m, 옆으로 몇 m"입니다.
탑다운도 시선도 각자 **로봇 기준 좌표**를 만들어냅니다.

### 길이 완전히 다른 두 경로

**탑다운 경로 — 한 단계**

```
화면 픽셀 (412, 238)
   ↓  호모그래피 (3×3 행렬 한 번 곱하기)
로봇 좌표 (0.28, -0.09)
```

끝입니다. 카메라가 고정돼 있고 책상이 평평해서 이게 가능합니다.

> **주의 — "오차 5mm"는 캘리브레이션을 제대로 했을 때의 이야기입니다.**
>
> 호모그래피는 **평면 ↔ 평면** 대응입니다. 그래서 캘리브레이션 점들이 전부
> **같은 높이(테이블면)** 에 있어야 합니다. 예전 버전은 캘리브 자세를 관절각으로
> 적어뒀는데, 그 자세들의 그리퍼 끝 높이가 3.6~13.1cm로 흩어져 있었습니다.
>
> 이러면 **캘리브레이션이 "합격"으로 보이면서 실제로는 틀립니다.**
> 같은 격자에서 수정 전후를 비교한 결과입니다:
>
> | 카메라 | 화면에 찍히는 재투영 오차 | 실제 테이블면 오차 |
> |---|---|---|
> | 수직 (수정 전) | 3.7mm (합격!) | 평균 17.9mm / 최대 44.7mm |
> | 15도 기울임 (수정 전) | 4.2mm (합격!) | 평균 57.5mm |
> | 수직 (수정 후) | 0.0mm | 평균 0.50mm |
> | 15도 기울임 (수정 후) | 0.0mm | 평균 1.86mm |
>
> 재투영 오차는 **캘리브 점 자신에 대해서만** 맞춘 숫자라 실사용 정확도를
> 보증하지 않습니다. 지금은 캘리브 지점을 테이블면 위 좌표로 적어두고
> 관절각을 역기구학으로 풀기 때문에 높이가 전부 같습니다.
>
> 그래도 **4단계에서 자로 재는 검증은 반드시 하세요.** 위 표가 보여주듯
> 화면에 찍히는 숫자만 보고는 틀린 걸 알 수 없습니다.

**시선 경로 — 네 단계**

```
1) 눈 카메라   "눈이 이 방향을 향한다"
                → 머리 기준 방향. 고개 돌리면 값이 바뀜

2) 스테레오    "저기까지 42cm"
                → 방향 + 거리 = 점 하나
                → 아직 "내 머리 기준" 좌표

3) SLAM        "내 머리가 지금 방 안 여기에, 이 자세로 있다"
                → 머리 기준 점 + 머리 위치 = 방 기준 점
                → p_W (0.62, 0.18, 0.31)

4) T_BW        "방 기준을 로봇 기준으로 번역"
                → p_B (0.29, -0.07)
```

오차 약 30mm. 단계가 많아서 오차가 쌓입니다.

### 3단계가 왜 필요한가

고개를 돌리면 1·2단계 숫자가 바뀝니다. 같은 컵인데도요.
하지만 SLAM 값도 같이 바뀌어서 **최종 결과는 그대로**입니다.
컵은 안 움직였으니까요.

**SLAM이 없으면 고개만 돌려도 로봇이 다른 데로 갑니다.**

### 4단계가 왜 필요한가

SLAM의 원점은 *"SLAM을 켠 순간 카메라가 있던 자리"*입니다.
오늘 책상 왼쪽에서 켰으면 거기가 (0,0,0)이고, 내일 오른쪽에서 켜면 원점이 옮겨갑니다.
로봇과 아무 관계가 없죠.

그래서 **둘 사이 관계를 한 번 측정해 둡니다.** 그게 `T_BW`입니다.
환율표 같은 겁니다. "5만"이라는 숫자만으로는 아무것도 못 하고,
원인지 달러인지 + 환율을 알아야 하는 것과 같습니다.

### 정리

```
탑다운:  화면 ──호모그래피──> 로봇 좌표          (1단계, 5mm)

시선:    눈 ──방향──> +스테레오 ──점──>
         +SLAM ──방 기준──> +T_BW ──> 로봇 좌표  (4단계, 30mm)
```

**둘 다 로봇 기준 좌표로 끝납니다.** 그래서 서로 비교할 수 있습니다.

## 8. 컵이 여러 개면 어떻게 구분하나 ★

7번을 이해했다면 이건 쉽습니다.

### 먼저, 오해부터 풀기

> **탑다운 카메라는 "어느 컵을 보는지" 모릅니다. 알 필요도 없습니다.**
> **씬카메라와 탑다운 카메라는 서로의 화면을 본 적이 없습니다.**
> **두 화면 사이에 변환 같은 것도 없습니다.**

역할이 이렇게 나뉩니다.

| 누가 | 뭘 아나 |
|---|---|
| 탑다운 | 컵들이 **어디** 있는지. 어느 걸 보는지는 모름 |
| 시선 | **어디**를 보는지. 정확한 위치는 잘 모름 |
| **target_resolver** | 위 둘을 받아서 **어느 컵인지 판단** |

판단하는 건 카메라가 아니라 **제3자인 노드**입니다.

### 친구 두 명 비유

친구 둘이 있습니다. 서로 말을 안 합니다.

- 친구 A(탑다운)가 쪽지: *"컵이 세 개. 각각 여기, 여기, 여기."*
- 친구 B(시선)가 쪽지: *"쟤가 여기를 보고 있음."*

당신은 두 쪽지만 받았습니다. 어느 컵을 보는지 알 수 있나요?
네, B가 적은 위치와 겹치는 컵을 찾으면 됩니다.

**A와 B는 서로 만난 적도 없습니다.** 두 쪽지를 겹쳐 보는 건 당신입니다.

### 실제 계산은 이게 전부

```python
cups = [(0.28, -0.18), (0.30, 0.00), (0.29, 0.18)]   # 탑다운이 준 것
gaze = (0.31, 0.03)                                   # 시선이 준 것

거리 = [0.213, 0.032, 0.152]
→ 1번 컵 선택
```

영상도 픽셀도 안 나옵니다. **숫자 세 쌍과 숫자 한 쌍의 거리 비교**입니다.

### 왜 이게 믿을 만한가

```
시선 오차   ●●●                     3cm
컵 간격     ●●●●●●●●●●●●●●●●●●     18cm
```

시선이 3cm 틀려도 정답 컵에서 3cm 벗어난 지점을 찍습니다.
다른 컵까지는 18cm예요. **잘못 고르려면 9cm는 틀려야 합니다.**

여섯 배 여유가 있어서, 시선에게 정밀도를 요구할 필요가 없습니다.

### 그래서 역할 분담이 이렇게 됩니다

```
시선   →  "왼쪽 컵"        (30mm 오차여도 OK)
탑다운 →  (0.28, -0.09)    (5mm 오차, 이 값이 로봇에 전달됨)
```

로봇이 실제로 가는 좌표는 **탑다운이 준 값**입니다.
시선은 "어느 것"만 정하고 빠집니다.
덕분에 시선 오차 30mm가 파지 정확도에 영향을 주지 않습니다.

### 한계도 분명히 있습니다

**컵이 6cm 이내로 붙어 있으면 이 방법은 깨집니다.**
오차 범위 안에 두 컵이 들어오니까요.

대책:
- **시연에서 컵을 15cm 이상 떨어뜨리기.** 꼼수가 아니라 시스템 사양입니다
- **애매하면 아예 거부하기.** 1등과 2등 거리 차가 5cm 미만이면 선택 안 함
  → `target_resolver`의 `ambiguity_margin`으로 구현돼 있습니다(기본 0.05m).
    걸리면 "어느 물체인지 모호합니다"라고 로그에 찍고 목표를 내지 않습니다.
- **고른 컵을 화면에 강조해서 사용자가 확인하게 하기** (아직 미구현)

틀린 컵을 집는 것보다 안 집는 게 낫습니다.
대상 사용자가 손을 못 쓰는 분이라면 되돌리기 어려우니까요.

같은 이유로 **물체를 아예 못 찾았을 때도 거부**할 수 있습니다
(`require_snap_for_pick`). 스냅 실패는 "정확한 컵 위치를 모른다"는 뜻이고,
그대로 진행하면 시선 오차 3cm가 그대로 파지 오차가 되기 때문입니다.
안경을 붙인 뒤에는 이 옵션을 켜고 씁니다(통합 런치가 자동으로 켭니다).

## 9. 어려운 개념 두 개

### 역기구학 (Inverse Kinematics)

**"손끝을 여기에 두려면 관절을 몇 도씩 꺾어야 하나"**를 푸는 계산입니다.

로봇이 컵을 집어본 경험이 없어도 됩니다.
**팔 길이를 알고 있으면 삼각형 문제로 풀리거든요.**

```
어깨 ──위팔 116mm── 팔꿈치 ──아래팔 135mm── 손끝
 └──────── 목표까지 거리 240mm ────────┘
```

세 변 길이를 알면 각도가 코사인 법칙으로 나옵니다. 경험이 아니라 **계산**이에요.

정확히는 해가 **두 개**입니다. 팔꿈치를 위로 접는 자세와 아래로 접는 자세죠
(`elbow_up`). 그리고 이 팔은 5자유도라 위치 3개를 맞추면 자유도가 하나 남는데,
그걸 **접근 피치각**(그리퍼가 비스듬히 내려오는 각도)으로 정합니다.

접근각은 "안 되면 더 가파르게"가 아니라 **컵까지 거리에 맞춰 고르는 값**입니다.
각도마다 닿을 수 있는 거리 띠가 다르기 때문입니다(테이블 위 파지 높이 기준):

| 접근각 | 닿는 반경 |
|---|---|
| 75도(가파름) | 0.20 ~ 0.29 m |
| 45도 | 0.26 ~ 0.35 m |
| 20도(얕음) | 0.30 ~ 0.38 m |

그래서 코드는 여러 각을 순서대로 시도합니다(`solve_with_fallback`).

검산도 됩니다. 나온 각도를 반대 방향 계산(순기구학)에 다시 넣어서
원래 좌표가 나오는지 보면 됩니다. 학습 모델은 이런 검증이 안 됩니다.

### 호모그래피 (Homography)

**"화면 픽셀 → 로봇 좌표"**를 바꿔주는 3×3 행렬입니다.

책상이 평평하기 때문에 가능합니다. 평면끼리는 이 행렬 하나로 완벽히 대응돼요.
덕분에 깊이 계산도, SLAM도 필요 없습니다. 7번에서 본 "한 단계"가 이겁니다.

구하는 법이 재밌는데, **로봇 자신을 자로 씁니다.**

1. 로봇팔을 특정 자세로 보냄 → 손끝이 로봇 기준 어디인지는 정확히 앎
2. 그 손끝이 화면 어느 픽셀인지 사람이 클릭
3. 4쌍 이상 모으면 행렬이 나옴

`T_BW` 캘리브레이션도 똑같은 원리입니다. 클릭 대신 응시할 뿐이에요.
**둘 다 "로봇 손끝을 기준점으로 쓴다"**는 점이 같습니다.

## 10. 개발 순서

자세한 절차는 `ROBOT_ONLY_TEST.md`에 있습니다. 여기선 큰 줄기만.

| 단계 | 하는 일 | 왜 이 순서인가 |
|---|---|---|
| 0 | 카메라·로봇 고정 | 나중에 움직이면 캘리브레이션 다시 |
| 1 | 팔 길이 숫자 입력 | 이게 틀리면 전부 틀림 |
| 2 | 서보 방향 확인 | 반대로 돌면 위험 |
| 3 | 호모그래피 캘리브레이션 | 화면 ↔ 로봇 좌표 연결 |
| 4 | **모터 끄고** 좌표만 확인 | 틀린 좌표로 움직이면 사고 |
| 5 | 재시도 로직 확인 | 실패 복구가 되는지 |
| 6 | 실제로 컵 집기 | 여기서 처음 진짜 움직임 |
| 7 | 30번 해보고 성공률 측정 | 보고서 숫자 확보 |
| 8 | 안경과 합치기 | 로봇 쪽이 완성된 뒤에 |

**4단계가 특히 중요합니다.** 모터를 켜기 전에 좌표가 맞는지 자로 재서 확인합니다.
여기를 건너뛰고 모터를 켜면 로봇이 책상을 찍을 수 있습니다.

### 8단계에서 바뀌는 것

| | 로봇 단독 | 통합 후 |
|---|---|---|
| 좌표 출처 | 마우스 클릭 | 시선 |
| `map` ↔ `base_link` | 항등변환 | `T_BW` 캘리브레이션 |
| 컵 위치 찾기 | 탑다운 | **탑다운 (그대로)** |
| 노드 ②④⑤ | — | 바뀌지 않음 |
| 노드 ③ `target_resolver` | — | **좌표 변환이 필요했습니다** ↓ |

> **초안에는 "노드 ②③④⑤가 한 줄도 안 바뀐다"고 적혀 있었는데, 그건 틀렸습니다.**
>
> 통합하면 두 입력이 **서로 다른 좌표계**로 들어옵니다.
>
> - 시선(`/gaze/fixation`) → SLAM world(`map`) 기준
> - 탑다운(`/objects/poses`) → 로봇 베이스(`base_link`) 기준
>
> ③이 이 둘을 변환 없이 거리 비교하면, 같은 컵인데도 수십 cm 떨어진 것으로
> 보입니다. 예를 들어 안경을 로봇 왼쪽 뒤 50cm에서 켜고 30도 틀어졌다면
> **같은 컵이 74cm 어긋난 것으로 계산**됩니다. 그러면 스냅이 실패하고,
> 억지로 스냅되더라도 ⑤가 변환을 한 번 더 걸어 엉뚱한 데로 갑니다.
>
> 로봇 단독 모드는 `map = base_link` 항등이라 **이 결함이 전혀 드러나지 않습니다.**
> 통합하는 날 처음 나타납니다.
>
> 그래서 ③이 **들어온 모든 점을 `base_link`로 변환한 뒤에** 비교하도록 고쳤습니다.
> 목표도 `base_link`로 내보내고, 어느 좌표계인지 메시지에 명시합니다
> (`GazeTarget.header.frame_id`). ⑤는 그 값을 보고 이미 로봇 기준이면
> 변환을 건너뜁니다.

## 11. 역할 나누기 제안

| 역할 | 할 일 | 필요한 것 |
|---|---|---|
| **A. 하드웨어** | 카메라 마운트, 로봇 고정, 그리퍼 개선 | 3D 프린터, 공구 |

A와 B는 병렬로 할 수 있습니다.
D는 완전히 독립이라 처음부터 따로 가도 됩니다.

## 12. 자주 나올 질문

**Q. 씬카메라가 본 컵을 탑다운 카메라가 어떻게 찾아내나요?**
안 찾아냅니다. 두 카메라는 서로를 모릅니다.
각자 **로봇 기준 좌표**를 만들고, `target_resolver`가 거리를 비교해서
같은 컵인지 판단합니다. 8번을 보세요.

**Q. 화면 픽셀끼리 변환하면 안 되나요?**
씬카메라는 머리에 달려 있어서 계속 움직입니다.
고개를 돌리면 같은 컵이 화면 완전히 다른 곳에 찍혀요.
변환을 매 프레임 다시 계산해야 하고, 결국 3D 좌표를 거쳐야 합니다.
돌아가는 길이라 오차만 커집니다.

**Q. SLAM은 왜 필요한가요?**
고개를 돌려도 같은 좌표가 나오게 하려고요.
SLAM이 없으면 고개만 돌려도 로봇이 다른 데로 갑니다. 7번을 보세요.

**Q. 로봇이 컵을 인식하는 건가요?**
아니요. 로봇은 컵이 뭔지 모릅니다. "이 좌표로 가서 그리퍼를 닫아라"를
실행할 뿐입니다. 그래서 컵을 한 종류로 고정해야 합니다.

**Q. 그럼 다른 물건은 못 집나요?**
크기와 모양이 비슷하면 됩니다. 손잡이가 있거나 너무 크거나 말랑하면 어렵습니다.
모든 물건을 다루려면 학습이 필요한데, 그건 이 프로젝트 범위 밖입니다.

**Q. 딥러닝은 안 쓰나요?**
컵 검출에 YOLO를 쓸 수는 있습니다(선택).
하지만 **동작 자체는 학습이 아니라 계산**입니다.
학습으로 하면 "시선이 목표를 정한다"는 우리 프로젝트의 핵심 주장이 흐려집니다.

**Q. 실패하면 어떻게 되나요?**
잡았는지 확인해서, 실패하면 최대 3번 다시 시도합니다.
3번 다 실패하면 안전하게 원위치로 돌아가고 사용자에게 알립니다.

**Q. 컵 두 개가 붙어 있으면요?**
6cm 이내면 구분이 안 됩니다. 시연에서는 15cm 이상 떨어뜨립니다.
이건 시스템 사양으로 명시할 내용입니다.

**Q. 안경 없이 개발하면 나중에 안 맞지 않나요?**
안 그렇습니다. 마우스 입력을 파이프라인 **맨 앞**에 넣었기 때문에,
그 뒤 노드 4개는 실제와 똑같이 동작합니다.

**Q. ROS2를 꼭 배워야 하나요?**
전부는 아닙니다. 명령어 세 개와
"노드는 작은 프로그램, 토픽은 데이터 통로" 이 개념만 알면 됩니다.

## 13. 한 장 요약

```
우리가 만드는 것:  눈으로 보면 로봇이 컵을 옮겨주는 시스템

로봇 쪽 역할:      좌표를 받아서 → 컵을 집어 → 옮긴다

지금 좌표 출처:    마우스 (나중에 시선으로 교체)


좌표를 만드는 두 경로 ─────────────────────────────

  탑다운:  화면 픽셀 ──호모그래피──> 로봇 좌표      (5mm)

  시선:    눈 방향 + 스테레오 거리 ──> 머리 기준 점
           + SLAM ──> 방 기준 점
           + T_BW ──> 로봇 좌표                     (30mm)

  둘 다 "로봇 기준"으로 끝나서 서로 비교 가능


컵 여러 개 구분 ───────────────────────────────────

  탑다운이 컵 목록을 주고, 시선이 점 하나를 주면
  target_resolver가 거리를 재서 가장 가까운 걸 고름

  시선   →  "어느 컵"     (대충 맞아도 됨)
  탑다운 →  "정확히 어디"  (이 값이 로봇에 전달)


핵심 기술:         역기구학   좌표 → 관절 각도
                   호모그래피  화면 픽셀 → 로봇 좌표
                   응시 판정   1.2초 머물러야 선택
                   파지 확인   그리퍼 덜 닫히면 물었다

개발 순서:         고정 → 숫자 입력 → 서보 확인 → 캘리브레이션
                   → 좌표 검증 → 재시도 검증 → 실제 파지
                   → 성공률 측정 → 안경과 통합

지금 목표:         파지 성공률 80% 이상
```
